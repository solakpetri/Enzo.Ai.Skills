# Rust Database

Use this skill when working on persistence code in Rust.

Inspect the repository first. Identify the database engine, the access crate (`sqlx`, `diesel`, `diesel-async`, `sea-orm`, `tokio-postgres`, `rusqlite`), how pools are configured, how data-access code is organized, the migration tool and directory, and how persistence is tested. Follow those choices. Do not introduce an ORM into a raw-SQL codebase, or the reverse, as part of an unrelated change.

Examples use `sqlx` with PostgreSQL because it is a common combination. Apply the same principles to other crates and engines.

Use `rust-backend` for service wiring, `rust-async` for concurrency, and `rust-testing` for database testing.

## General Principles

- The database is the final guardian of data integrity. Constraints enforce invariants that application code cannot guarantee under concurrency.
- Know exactly which SQL each operation runs, whether it is written by hand or generated by an ORM.
- Keep transactions short and explicit.
- Measure query performance with real plans (`EXPLAIN ANALYZE`) and realistic data volumes.

## Connection Pools

- Create one pool per database at startup and share it through application state. `sqlx::Pool` is reference-counted and cheap to clone.
- Size `max_connections` against the database's connection limit divided across all service instances, workers, and migration jobs. Bigger pools are not automatically faster.
- Set `acquire_timeout` so requests fail fast instead of queuing forever when the pool is exhausted.
- Set `idle_timeout` and `max_lifetime` appropriately for connection proxies, failovers, and credential rotation.
- Do not hold a connection or transaction across slow external work such as HTTP calls, message publishing, or user-facing waits. This is the most common cause of pool exhaustion.
- Treat `PoolTimedOut` as a saturation signal. Investigate held connections and slow queries before increasing the pool size.

## Data-Access Structure

- Group queries by domain area in plain functions or small structs. Do not wrap the database in a generic `Repository<T>` trait that only duplicates the crate's API.
- Write data-access functions that accept a connection or executor (`&mut PgConnection`, or `impl PgExecutor<'_>`) rather than the pool. The same function can then run inside or outside a transaction.
- Introduce a repository trait only at a real seam, such as multiple storage backends or a fake required for tests of complex application logic.
- Keep persistence row types separate from API types when their shapes or lifecycles differ.

```rust
pub async fn insert_order(
    conn: &mut PgConnection,
    order: &NewOrder,
) -> Result<OrderId, sqlx::Error> {
    sqlx::query_scalar!(
        "INSERT INTO orders (customer_id, total_cents) VALUES ($1, $2) RETURNING id",
        order.customer_id,
        order.total_cents,
    )
    .fetch_one(conn)
    .await
    .map(OrderId)
}
```

## Queries

- Prefer compile-time checked queries (`sqlx::query!`, `query_as!`, Diesel's DSL) when the repository uses them. Commit the offline query metadata (`.sqlx/` from `cargo sqlx prepare`) so CI builds without a database.
- Select explicit columns instead of `SELECT *`, so schema additions do not change mapping or over-fetch.
- Filter, sort, aggregate, and paginate in the database, not in Rust after fetching.
- Choose the fetch method by cardinality: `fetch_one` when exactly one row is required, `fetch_optional` when zero or one is valid, `fetch_all` only for bounded result sets, and `fetch` (a stream) for large ones.
- Use deterministic ordering whenever results are paginated or order matters. Include a unique tiebreaker column.
- Never return unbounded result sets from request paths.

## Avoiding N+1 Queries

- Do not run a query inside a loop over results. Batch with `WHERE id = ANY($1)`, a join, or the ORM's eager-loading facility (Diesel's `belonging_to`, SeaORM's loaders).
- Assemble parent-child structures in Rust from batched results using a `HashMap` keyed by parent ID.
- Watch for N+1 patterns hidden behind helper functions called per item.

## Transactions

- Begin transactions explicitly (`pool.begin()`, `conn.transaction(...)`) at the application-logic level that owns the unit of work. Pass `&mut *tx` to data-access functions.
- With `sqlx`, a transaction that is dropped without `commit()` rolls back. An early return via `?` therefore rolls back, which is correct. Forgetting `commit()` on the success path is a silent bug.
- Keep transactions short. Do not perform network calls, file I/O, or long computations inside them.
- Do not spawn tasks that use a transaction. A transaction is bound to a single connection and must be used sequentially.
- Know the default isolation level (PostgreSQL uses `READ COMMITTED`) and raise it deliberately when the invariant requires it.
- Under `SERIALIZABLE` or `REPEATABLE READ`, retry the whole transaction on serialization failures (`40001`) and deadlocks (`40P01`), with a bounded attempt count.
- Use the transactional outbox pattern when a database change must reliably produce a message. Do not publish to a broker inside the transaction and hope both succeed.

## Concurrency Control

- Identify the invariant at risk before choosing a mechanism.
- Use optimistic concurrency with a version column for user-facing edits: `UPDATE ... SET version = version + 1 WHERE id = $1 AND version = $2`, then check `rows_affected()`. Zero rows means a conflict, so return `409` or retry.
- Use `SELECT ... FOR UPDATE` for short read-modify-write sections where conflicts are frequent.
- Use atomic SQL (`UPDATE accounts SET balance = balance - $1 WHERE id = $2 AND balance >= $1`) instead of read-then-write in Rust.
- Use `INSERT ... ON CONFLICT` for idempotent upserts instead of check-then-insert.
- Use advisory locks only for coordination the schema cannot express, and release them reliably.

## Constraints And Error Mapping

- Enforce invariants with `NOT NULL`, `UNIQUE`, `CHECK`, foreign keys, and exclusion constraints, not only in Rust.
- Map constraint violations to domain errors explicitly. With `sqlx`, inspect `Error::Database` and use `is_unique_violation()`, `is_foreign_key_violation()`, or the constraint name.
- Name constraints so error mapping can distinguish them.
- Do not pre-check uniqueness with a `SELECT` and treat that as sufficient. Concurrent requests race between the check and the insert. Rely on the constraint and map the error.

```rust
match insert_user(&mut conn, &user).await {
    Ok(id) => Ok(id),
    Err(sqlx::Error::Database(e)) if e.constraint() == Some("users_email_key") => {
        Err(UserError::EmailTaken)
    }
    Err(e) => Err(UserError::Database(e)),
}
```

## Indexes

- Index columns used in frequent filters, joins, foreign keys, and ordering for pagination.
- Match composite index column order to query predicates and sort order.
- Use partial indexes for queries over a small, frequently accessed subset, such as pending jobs.
- Do not add indexes speculatively. Every index costs write throughput and storage. Verify with `EXPLAIN ANALYZE`.

## Pagination

- Prefer keyset (cursor) pagination for large or frequently changing tables: `WHERE (created_at, id) < ($1, $2) ORDER BY created_at DESC, id DESC LIMIT $3`.
- Use `OFFSET` pagination only for small tables or admin views where deep pages are rare.
- Cap page size on the server.
- Encode cursors opaquely when they are exposed to clients.

## Bulk Operations

- Insert many rows in one statement with `UNNEST` arrays, `QueryBuilder::push_values`, or `COPY` for large loads, instead of looping over single inserts.
- Chunk very large batches to respect parameter limits (65,535 bind parameters in PostgreSQL) and transaction size.
- Update or delete in set-based statements rather than row-by-row loops.

## Dynamic SQL Safety

- Never build SQL with `format!` and user input. Use bind parameters for every value.
- Use `QueryBuilder` with `push_bind` for dynamic filters. Use `push` only for trusted SQL fragments.
- Map user-controlled sort fields and directions through an allowlisted enum, never interpolate them.
- Avoid string-built `IN (...)` lists. Use `= ANY($1)` with an array bind.

## Type Mapping

- Use exact decimal types (`rust_decimal`, `bigdecimal`) or integer minor units for money. Never use `f64`.
- Use timezone-aware timestamps (`timestamptz` with `time::OffsetDateTime` or `chrono::DateTime<Utc>`).
- Map database enums to Rust enums with `sqlx::Type` or the ORM's equivalent, and keep both in sync through migrations.
- Use newtypes for IDs (`#[sqlx(transparent)]`) so different entity IDs cannot be mixed up.
- Make nullability in Rust types match the schema. Use `query!` overrides (`"col!"` or `"col?"`) only when the inference is wrong and you can explain why.

## ORMs And Sync Crates

- Diesel's core API is synchronous. In async services, use `diesel-async` or run Diesel calls in `spawn_blocking` through a pool such as `deadpool-diesel`. Never call synchronous Diesel directly on a runtime worker thread.
- With SeaORM, review the generated SQL for important queries and use explicit loaders or joins for related data.
- Drop to raw SQL for complex queries when the ORM's version is harder to read or produces a poor plan. Keep it parameterized and tested.

## Migrations

- Use the repository's migration tool (`sqlx migrate`, Diesel migrations, `refinery`, SeaORM migrations).
- Never edit a migration that has been applied anywhere shared. `sqlx` verifies checksums and will refuse to run. Add a new migration instead.
- Write migrations that are safe while the old application version is still running. Use expand-and-contract for renames and type changes: add, backfill, switch readers and writers, then remove.
- Avoid long locks on large tables. In PostgreSQL, use `CREATE INDEX CONCURRENTLY` (outside a transaction, using the tool's no-transaction mode), add constraints as `NOT VALID` and validate later, and set a `lock_timeout`.
- Backfill large tables in batches, not in a single statement inside the migration.
- Decide how migrations run in deployment (startup, a separate job, or CI) and make sure concurrent instances cannot run them simultaneously in an unsafe way.
- Review generated or hand-written migrations for destructive operations, data loss, and nullability changes.

## Job Queues In The Database

- Claim jobs with `SELECT ... FOR UPDATE SKIP LOCKED LIMIT n` inside a short transaction.
- Make job handlers idempotent. Jobs can run more than once after crashes or timeouts.
- Track attempts and move poison jobs to a failed state after a limit.
- Use a lease or heartbeat timeout to recover jobs from crashed workers.

## Caching

- Cache only with a clear invalidation strategy and an acceptable staleness bound.
- Do not treat a cache as the source of truth.
- Protect against stampedes for expensive cache misses.

## Diagnostics

- **Slow query:** capture the SQL and parameters, run `EXPLAIN (ANALYZE, BUFFERS)`, and check for sequential scans, misestimated row counts, and missing indexes.
- **Pool exhaustion:** look for connections held across awaits on external calls, long transactions, leaked transactions in spawned tasks, and N+1 loops.
- **Deadlocks:** look for inconsistent lock ordering across transactions. Make update order deterministic, such as sorting by ID.
- **Lost updates:** look for read-modify-write in Rust without version checks or row locks.
- Enable statement logging at debug level with slow-query thresholds (`sqlx` `ConnectOptions::log_slow_statements`), without logging sensitive parameters in production.

## Common Anti-Patterns

- Generic repository traits that only wrap the access crate.
- Check-then-insert without a unique constraint.
- Read-modify-write in application code without concurrency control.
- Queries in loops.
- Unbounded `fetch_all` on request paths.
- Holding a transaction across HTTP calls.
- Floats for money.
- `format!`-built SQL.
- Editing applied migrations.
- Blocking Diesel calls on async worker threads.

## Implementation Workflow

- Inspect the access crate, pool configuration, data-access layout, migrations, and test setup.
- Identify the invariant and the consistency requirement for the change.
- Write the schema change as a new, deployment-safe migration if needed.
- Write queries with explicit columns, bind parameters, bounded results, and deterministic ordering.
- Decide transaction scope and concurrency control explicitly.
- Map constraint violations to domain errors.
- Refresh offline query metadata if the repository uses it.
- Test against the real engine, including conflict and constraint cases.

## Review Checklist

- Does the change follow the repository's access crate and data-access conventions?
- Are queries parameterized, with no SQL built from user input?
- Are columns explicit and result sets bounded?
- Is ordering deterministic where it matters?
- Are N+1 patterns avoided?
- Are transaction boundaries explicit, short, and committed on success?
- Is no connection or transaction held across external I/O?
- Is the concurrency-sensitive invariant protected by constraints, version checks, row locks, or atomic SQL?
- Are constraint violations mapped to meaningful errors?
- Are money and time types correct?
- Are migrations new, reversible or forward-safe, and non-blocking for large tables?
- Is offline query metadata updated?
- Are persistence tests run against a realistic database?
